# 公文写作AI系统——整体架构设计方案

**面向烟草行业管理咨询 · 个人工作站方案**

版本：v2.0（实态对齐版）| 2026年3月16日

> **v2.0 更新说明**：本版基于知识库Phase 1-5实际交付成果，对v1.0的规划数据全面刷新为真实数据，新增段落库/金句库的RAG接入设计，修正模板库分类体系，补充Dify知识库的具体导入映射方案。

## 一、设计定位与核心决策

### 1.1 一句话定义

这是一套**部署在本地服务器上的多Agent公文写作流水线**，以Dify工作流引擎为核心平台，接入DeepSeek/Qwen大模型，通过"四库一引擎"知识体系提供知识支撑，覆盖从意图识别到终稿输出的完整公文生成链路。重点服务六个使用场景：**讲话、方案、计划、汇报、报告、规划**。

### 1.2 三个核心决策

**决策一：平台选 Dify，不从零写代码。**

你是管理咨询顾问，不是全职开发者。Dify 提供可视化工作流编排 + 内置RAG知识库 + Docker本地部署，三个能力刚好覆盖你的三个硬需求。六个Agent用拖拽连线实现，条件分支（审核不通过回环到起草）用IF/ELSE节点完成，不需要手写LangGraph的Python代码。

与其他方案的对比：

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| **Dify（推荐）** | 可视化编排、内置RAG、Docker部署、API发布 | 复杂逻辑定制性弱于纯代码 | **最佳选择** |
| LangGraph + CrewAI | 灵活度最高，条件分支精细控制 | 开发量大、需Python能力、维护成本高 | 后期可选迁移 |
| Claude Code | 命令行操作、适合代码项目 | 不适合工作流编排、无RAG管理界面 | 不适用 |
| Coze/扣子 | 无代码、可部署到微信/飞书 | 绑定字节生态、数据上云、不可本地化 | 不满足安全要求 |
| FastGPT | 轻量RAG、可视化Flow | 多Agent编排能力弱 | 不满足流水线需求 |

**决策二：大模型主力用 DeepSeek，备选 Qwen。**

DeepSeek-V3 的中文公文生成质量和成本效益比（¥1/百万token）在评估的五个模型中最优。Qwen-2.5-72B 作为完全断网部署的备选（需GPU本地推理）。Claude 可作为辅助模型用于结构审核和逻辑检查，但不作为主力生成模型——它对中文公文的政治术语和行文习惯不如国产模型熟悉。

| 模型 | 角色定位 | 部署方式 | 适用环节 |
|------|---------|---------|---------|
| **DeepSeek-V3** | 主力生成 | API调用（¥1/1M tokens） | 起草、润色、金句推荐 |
| **Qwen-2.5-72B** | 断网备选 | 本地推理（需A100或2×4090） | 全流程替代DeepSeek |
| **Claude** | 辅助审核 | API调用 | 结构逻辑审核、大纲优化 |

**决策三：全链路本地化部署，不碰云端。**

烟草行业是国家专营，年税利超1.6万亿，文档包含商业和政治敏感信息。**没有任何烟草国企会把内部文件送到外部API。** 整个系统部署在本地服务器上：Dify（Docker）+ 向量数据库（Milvus自托管）+ LLM推理。如果用DeepSeek API，仅将脱敏后的通用写作请求发送到API，历史交付物和客户资料绝不出本地。

## 二、系统总体架构

### 2.1 四层架构

整个系统分为四层，从上到下依次为：

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：用户交互层                                          │
│  Dify WebUI（浏览器访问）/ API接口（供未来OA系统对接）       │
└─────────────────────────┬───────────────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────────────┐
│  第二层：Agent工作流层（Dify Workflow Engine）                │
│  六个Agent串联流水线，带条件分支回环                          │
│  ① 意图分析 → ② 知识检索 → ③ 起草 → ④ 格式审核             │
│  → ⑤ 术语校对 → ⑥ 润色 → 人工审核 → 输出                   │
└─────────────────────────┬───────────────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────────────┐
│  第三层：知识库层（四库一引擎 + 段落库/金句库扩展层）          │
│  Prompt模板库(151) / 规则引擎(15) / 词典库(606+)            │
│  语料库(90范文+330段落+394金句) / 元数据索引                  │
│  存储：Dify Knowledge Base（内置）+ Milvus（可选外挂）        │
│  Embedding：BGE-large-zh-v1.5（1024维）                      │
└─────────────────────────┬───────────────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────────────┐
│  第四层：基础设施层                                          │
│  Ubuntu Server + Docker Compose                              │
│  Dify全家桶（API+前端+PostgreSQL+Redis+Weaviate）            │
│  LLM推理：DeepSeek API / Qwen本地（可选）                    │
│  文档渲染：python-docx + GB/T 9704 Word模板                  │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 六Agent流水线设计

流水线是整个系统的核心，六个Agent各司其职，通过Dify工作流引擎串联。

#### Agent ①：意图分析Agent

- **职责**：接收用户自然语言输入，识别使用场景、子类型、行业、关键参数
- **输入**：用户原始请求（如"帮我写一份河南中烟管理成熟度评价推进方案"）
- **输出**：结构化意图对象
- **场景分类**：基于模板库实际索引，映射到六个使用场景
- **实现**：Dify中的LLM节点，System Prompt要求输出JSON

```json
{
  "usage_scenario": "方案",
  "sub_type": "实施方案",
  "industry": "烟草",
  "topic": "管理成熟度评价",
  "target_org": "河南中烟",
  "word_count": "5000-8000",
  "tone": "正式公文体"
}
```

#### Agent ②：知识检索Agent

- **职责**：根据意图分析结果，并行查询多个知识库，汇聚上下文
- **五路检索**（相比v1.0新增段落库独立检索）：
  - 模板库 → 通过`by_usage_index.json`按场景精确匹配模板
  - 词典库 → 检索行业术语、公文用语、禁用词（按industry + topic过滤）
  - 语料库·范文 → 召回高评分历史范文（优先8分以上的30份高价值文件）
  - 语料库·段落 → 按位置（开头/结尾/关键段落）检索可复用段落
  - 规则库 → 加载适用的质量标准和结构要求
- **检索策略**：混合检索（向量语义 + BM25关键词），Reranker二次排序
- **实现**：Dify中的Knowledge Retrieval节点，配置多个Knowledge Base

#### Agent ③：起草Agent（核心）

- **职责**：基于模板+检索结果+规则约束，调用LLM生成初稿
- **Prompt组装逻辑**：

```
[System Prompt]   ← 来自Prompt模板库的prompt_system字段
[写作规则]        ← 来自规则引擎的适用规则
[参考范文片段]    ← 来自语料库的Top-3高评分范文片段
[开头段落参考]    ← 来自段落库的同场景开头段落（2-3个）
[结尾段落参考]    ← 来自段落库的同场景结尾段落（1-2个）
[行业术语]        ← 来自词典库的烟草术语 + 公文用语
[用户指令]        ← 来自Prompt模板库的prompt_template，填入用户变量
```

- **调用模型**：DeepSeek-V3（主力）
- **输出**：公文初稿全文

#### Agent ④：格式审核Agent

- **职责**：检查初稿是否符合GB/T 9704格式规范和文种结构要求
- **规则来源**：`02_rules/format_compliance/` + `02_rules/gbt9704_standard.json`
- **检查项**：
  - 标题层级是否符合"一、→ (一) → 1. → (1)"递进规则
  - 文种结构完整性（如方案是否包含：背景→目标→原则→任务→保障）
  - 结尾套语是否规范（如汇报以"以上汇报，请审阅。"结尾）
  - 数字表述是否统一（阿拉伯数字 vs 汉字数字）
- **实现**：Dify中的LLM节点，System Prompt加载format_compliance规则集
- **输出**：审核结果（通过 / 不通过 + 具体问题列表）
- **不通过处理**：通过Dify条件分支回环到Agent ③，附带修改指令

#### Agent ⑤：术语校对Agent

- **职责**：检查口语化表述、术语准确性、公文禁用词
- **规则来源**：`02_rules/language_style/` + `03_dictionary/official_terms_v2.yaml`
- **检查项**：
  - 禁用词检测（PW模块65+条禁用表述）
  - 搭配规范校验（MM模块45+条搭配规范）
  - 套话替换建议（CP模块27+条替换规则）
  - 烟草行业术语准确性（TT模块65+条术语）
  - 口语→公文转换
- **实现**：Dify中的LLM节点，System Prompt加载language_style规则集 + 词典v2.0
- **输出**：校对结果（通过 / 不通过 + 替换建议列表）
- **不通过处理**：同样回环到Agent ③

#### Agent ⑥：润色Agent

- **职责**：对通过审核的文稿进行风格提升
- **素材来源**：`03_dictionary/金句库(P4).yaml`（394条）+ 排比句库（93条）+ 比喻词库（126条）
- **润色维度**：
  - 排比句增强（从排比句库检索同主题排比句式）
  - 金句插入（从394条金句中检索适合开头引题/结尾升华的句子）
  - 比喻手法增强（从比喻词库检索恰当比喻）
  - 开头/结尾优化（从段落库的开头段落73个+结尾段落82个中检索参考）
  - 语气调整（确保公文体的庄重感，去除"AI味"）
- **实现**：Dify中的LLM节点 + Knowledge Retrieval节点

#### 人工审核节点

- **职责**：在Dify WebUI上展示润色后的终稿，供人工审阅
- **操作选项**：通过（进入输出）/ 局部修改（标注修改意见回环到Agent ⑥）/ 驳回重写（回环到Agent ③）
- **实现**：Dify的Human-in-the-loop功能

### 2.3 条件分支与回环机制

```
                    ┌──── 不通过（附修改指令）────┐
                    │                              │
                    ▼                              │
  ① 意图分析 → ② 知识检索 → ③ 起草 → ④ 格式审核 ─┤
                                                   │
                                    ┌── 不通过 ────┤
                                    │              │
                                    ▼              │
                               ⑤ 术语校对 ─────────┘
                                    │
                                  通过
                                    │
                                    ▼
                               ⑥ 润色 → 人工审核 → 输出Word
```

回环规则：
- 每次回环携带具体的修改指令（不是从头生成，而是定向修改）
- 最多回环2次，超过则直接进入人工审核由人工修改
- 回环时只重新生成有问题的部分，不重写全文

## 五、文档输出层

### 5.1 Word文档渲染

使用 **python-docx** + **python-docx-template (docxtpl)** 实现GB/T 9704格式合规输出。

预设每个文种的`.docx`模板，格式已内置：

| 格式项 | 规范要求 |
|--------|---------|
| 标题字体 | 方正小标宋简体，二号 |
| 正文字体 | 仿宋_GB2312，三号（16磅） |
| 一级标题 | 黑体 |
| 二级标题 | 楷体_GB2312 |
| 行距 | 固定值29磅 |
| 页边距 | 上37mm、下35mm、左28mm、右26mm |
| 纸张 | A4 |

### 5.2 渲染流程

```
LLM生成的纯文本内容
    ↓
python脚本解析结构（识别标题层级、段落、列表）
    ↓
docxtpl填充到预设Word模板的对应槽位
    ↓
输出格式合规的.docx文件
    ↓
提供下载（Dify WebUI）或API返回
```

这个python脚本大约100-200行，是整个系统中唯一需要手写的代码。

## 七、解决"AI味"问题

这是实际使用中的头号挑战。AI生成的公文容易"生硬、模板化"，资深笔杆子一眼就能看出来。

### 7.1 四层消除策略（基于实际知识库强化）

**第一层：Few-shot范文注入（最有效）。** 每次生成时，从90份范文中检索2-3份高评分（≥8分）范文片段作为few-shot示例。30份A级高价值文件是核心素材池。

**第二层：段落级参考注入（v2.0新增）。** 从330个段落库中按位置（开头/结尾/关键段落）检索同场景段落，让LLM"照着你的风格"写开头和结尾。这比全文参考更精准——开头和结尾是最容易暴露"AI味"的部分。

**第三层：金句和排比句植入。** 润色Agent从394条个人金句 + 93条排比句 + 126条比喻词中检索适合当前主题的表达，替换AI生成的平淡表述。这些金句来自你自己的历史交付物，风格高度一致。

**第四层：禁用词和套话替换。** 词典v2.0的PW模块（65条禁用词）+ CP模块（27条套话替换）在校对环节自动清洗典型的AI生成痕迹。

### 7.2 长期优化路径

当积累了足够多的审核通过文档后（50+份），可以考虑对DeepSeek或Qwen基座模型做LoRA微调，让模型直接学会你的写作风格。参数建议：`lora_rank=8`，目标模块`q_proj`和`v_proj`，QLoRA可在单张24GB GPU上训练33B模型。

## 十、数据安全设计

### 10.1 安全原则

| 原则 | 具体措施 |
|------|---------|
| 数据不出本地 | Dify + 向量数据库 + 知识库文件全部本地部署 |
| API调用最小化 | 仅将脱敏后的通用写作请求发送到DeepSeek API |
| 历史交付物零泄露 | 90份个人交付物仅在本地RAG中使用，永不上传到任何云端 |
| 客户信息脱敏 | 如用云端API，自动替换：公司名→代称，财务数据→模糊值，人名→删除 |
| 完全断网可选 | 切换到Qwen本地推理后，可实现完全离线运行 |

### 10.2 部署优先级

**推荐路径**：先用DeepSeek API（最低成本、最快上线），将来如果客户有完全断网要求，再迁移到Qwen本地推理。两种模式在Dify中切换只需要改一个LLM配置项。

## 附录A：完整流程示例

**用户输入**：`帮我写一份河南中烟管理成熟度评价推进方案`

**Agent ① 意图分析输出**：
```json
{
  "usage_scenario": "方案",
  "sub_type": "实施方案",
  "industry": "烟草",
  "topic": "管理成熟度评价",
  "target_org": "河南中烟"
}
```

**Agent ② 知识检索执行**（五路并行）：
- 模板库 → `by_usage_index.json` 的"方案"场景命中21个模板，选Top-1
- 词典库 → 从`official_terms_v2.yaml`(TT模块)召回"管理成熟度""评价体系""工商协同"
- 范文库 → 从`优质范文库(P3).yaml`命中评分8分的方案类范文3份
- 段落库 → 从`段落库(P4).yaml`命中方案类开头段落2个+结尾段落2个
- 规则库 → 加载`content_quality/`中的方案结构完整性清单

**Agent ③ 起草**：基于模板+范文片段+段落参考+规则，调用DeepSeek生成6000字初稿

**Agent ④ 格式审核**：加载`gbt9704_standard.json`+`format_compliance/`检查标题层级和结构 → 通过

**Agent ⑤ 术语校对**：加载`official_terms_v2.yaml`(PW+MM模块)检查禁用词和搭配 → 发现2处口语表述，回环修改

**Agent ⑥ 润色**：从`金句库(P4).yaml`的394条中检索方案类金句，在"总体目标"段添加排比句，在结尾插入升华表述

**人工审核**：你在WebUI上查看终稿，微调几处表述 → 确认通过

**输出**：python-docx渲染为GB/T 9704格式的Word文件，下载保存

## 附录B：v1.0 → v2.0 变更清单

| 变更项 | v1.0（规划值） | v2.0（实态值） | 影响 |

| 模板分类 | 按四文种分目录 | 按素材类型分4目录+场景索引 | Agent ②检索逻辑需适配索引 |

| 词典结构 | 四个子库 | **六大子库**（新增句式库、分模块词典v2.0） | Dify KB数量增加 |
