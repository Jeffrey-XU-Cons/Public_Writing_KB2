## 一、为什么用 kb-rag 而不是自研

三条实打实的理由，不是偏好：

**一，它的规格是拿事故换来的，自研会把同样的坑再踩一遍。** SKILL.md 里记着至少 10 类静默失败（文件名与内容不同步、分隔符不一致、agent 互相写重、拼表格不转义竖线……），每条都标着实测数据。最典型的是答案长度上沿：定 2000 时派 12 个 agent 回压 453 条，只压掉 44 字/条，最后承认是「规则在跟自己的规格打架」，改成 2300。**这类结论无法靠设计推导出来，只能靠撞。**

**二，唯一校验器 + 批量流水线已经成型。** `qa_check.py` 是生成端、校对端、合并端共用的同一份口径（血泪来源：手写合并脚本漏了长度上限，150 条里混着 6822 字的条目照样报「全部合格」）。配套还有 `qa_merge`（合并重编号）、`qa_reconcile`（逐组对账，抓掉线分片）、`qa_genrun`（生成运行副本）、`export_xlsx`（交付格式）。第四章的十步 SOP 目前只有文字描述，脚本一个都还没写。

**三，7 层答案结构正好补上公文知识的短板。** 尤其第 4 层反向思维（失败路径 + 事前验尸 + 避坑清单）——公文写作最值钱的恰恰是「这么写会被打回来」，而 305 篇技巧汇编里大量内容就是在讲这个。现有 `rules_master` 的平表条目完全承载不了这类知识。

**代价要说清**：kb-rag 的答案规格是 1200–2300 字，比第四章原定的「条文型 ≥150 字」重得多。**不是所有公文知识都值得写 1500 字**（「公文用中文全角引号」写 150 字足够）。所以要做 §2.3 的双档处理。

## 二、schema 对齐（迁移的核心工作）

### 2.1 两边字段对照

| kb-rag 6 列 | 第四章 JSONL 字段 | 处理 |
|---|---|---|
| 序号 | `id`（`QA-C{n}-{5位}`） | 合并时重编号，沿用第四章 id 规则 |
| 问题（5–10 个 ` / ` 分隔，含加粗反向问法） | `question` + `question_keywords` | **kb-rag 规格更严**（第四章只要 3–6 个、无反向问法硬信号），采纳 kb-rag |
| 答案（7 层） | `answer` + `answer_type` | 见 §2.3 双档 |
| 标签（5–12） | `tags` | 一致，直接对应 |
| 应用场景（四段式） | `scenarios` | 一致（第四章本就是四段式，同源） |
| 问题关键词（8–15） | `question_keywords` | 一致 |
| — | `category_l1/l2`、`doc_types` | **kb-rag 没有**，入库时补（§2.2） |
| — | `depth`/`enforce`/`implements`/`derives_from`/`tobacco_fit`/`confidence` | **07 章 v2 新增**，入库时补 |
| — | `source_path`/`source_anchor`/`batch_id`/`status`/`answer_hash` | 入库脚本自动回填 |

**结论**：kb-rag 产出的 6 列是**核心内容层**，第四章的分类与治理字段是**外围元数据层**。迁移不是改 kb-rag，是在它后面接一个「打标入库」环节。

### 2.2 新增 `qa_tag.py`：6 列 → JSONL 的桥

kb-rag 产出 md 表格 → 本脚本逐条打标并转 JSONL：

```
输入：RAG_{主题}_{N}条QA.md
处理：① 解析 6 列（直接 import qa_check.split_row，不另写解析器）
     ② LLM 打标：category_l1/l2、doc_types、depth、enforce、tobacco_fit
     ③ 规则打标：answer_hash、batch_id、status、created
     ④ 挂钩链：implements/derives_from（需人工确认，见 §五风险）
输出：追加进 knowledge\qa\c{n}_*.jsonl
```

这是唯一需要**新写**的脚本。其余全部复用。

### 2.3 双档答案规格（对 kb-rag 的唯一实质修订）

公文知识有一类是「条文」——`GB/T 9704 规定成文日期用阿拉伯数字`，这条写 1500 字是注水。强行套 7 层会逼着模型编内容，直接违反 kb-rag 铁律一（真实性第一）。

修订：`qa_check.py` 增加 `--profile` 参数，两档并存。

| 档 | 适用 | 答案规格 | 层要求 | 对应 depth |
|---|---|---|---|---|
| `full`（默认，即 kb-rag 原规格） | 方法、原则、公理、场景实战 | 1200–2300 字，硬上限 2500 | 7 层齐全，反向层必配 | method/principle/axiom |
| `lite`（新增） | 条文、单点技巧 | **200–600 字** | 3 层：**结论 → 依据 → 正误对照**；反向层可合并进「正误对照」 | rule/technique |

判定规则（写进 SKILL，不靠人拍）：

```
这条知识能不能举出「做错了会怎样」的完整失败路径？
  能 → full 档
  不能，只是「规定如此」 → lite 档
```

预估分布：C2 形、C4 肉 以 lite 为主；C3 架、C5 用、C6 魂 以 full 为主；C1 骨 两者皆有。

**批次分布闸门同时适用于 lite 档**（lite 落在 500–600 的不得超三分之一），原因与 full 档一致——模型天然把上沿当目标。

### 3.4 新增的脱敏铁律

kb-rag 原铁律一是「绝不捏造」。公文项目要加一条**反向**约束：

```
铁律 8（脱敏）：QA 的问题、答案、案例中一律不得出现
  - 真实客户单位名 → 写〔A 省中烟〕〔B 市局〕
  - 具体经营数据   → 写〔数据〕，保留量纲与对比关系
  - 真实人名       → 删除，保留职务
与铁律一（不捏造）的关系：脱敏是「模糊化」不是「篡改」——
把「河南中烟 2023 年销量 X 万箱」写成「〔A 省中烟〕某年销量〔数据〕万箱」合法；
把它写成一个虚构的具体数字，违反铁律一。
```

这条必须写进 SKILL 而不只是写进设计文档——萃取时 agent 读的是 SKILL。

## 六、待你拍板的四条

**① 检索栈方案**（§4.2）：A 自建 venv ／ B 全局模型缓存 ／ C 顺带换 LanceDB。
建议 **B+C**。

**② 词典入库门槛**（07 章 v2 §2.4）：1,242 候选收哪些。
建议**频次 ≥100 且含行业专有词根**（卷烟/烟叶/专卖/终端/货源/配送/精益/对标/成熟度…），预估收 300–500 条。

**③ 讲评型篇目**（阶段 3.5）：A 先跳过，只做技巧型看够不够；B 上 LLM 段落级切分（约 35 万字）。
建议 **A**，理由是首件校准后才知道边际收益。

**④ 脱敏占位符粒度**（07 章 v2 §3.4）：`〔某省中烟〕` 统一占位 ／ `〔A 省中烟〕` 带编号。
建议**带编号**——段落常跨句指代同一单位，统一占位会让段落读不通。

## 七、风险登记

| 风险 | 影响 | 对策 |
|---|---|---|
| **挂钩链需人工确认** | `implements`/`derives_from` 靠 LLM 猜会大面积错挂，孤儿拦截形同虚设 | 阶段 3.1 先把 axiom/principle 全抽完并人工定稿，后续 method/technique 只在既定集合里选，选不中即报孤儿 |
| lite 档被滥用 | 模型图省事，该写 full 的写成 lite | `qa_check` 增校验：`depth` 为 method/principle/axiom 而 profile 为 lite → 报错 |
